# Kubernetes deployment assets

These are operator templates, not an installer for existing clusters. Native adapters are qualified on a dedicated two-node k3d 5.9.0 / K3s 1.35.9 cluster. Repeat network/PID/storage qualification for your environment. See [the complete configuration reference](../../docs/kubernetes.md).

1. Choose a dedicated cluster/context. Every command below must include `--kubeconfig /absolute/private/config --context your-context`. Do not change the global current context. A direct-process controller needs an explicit kubeconfig restricted to the supplied RBAC; an in-cluster controller uses the `flumic-controller` ServiceAccount.
2. Review namespace names, then apply `namespaces.yaml`. Apply `admission-policy.yaml` as a cluster operator and inspect the policy's `status.typeChecking.expressionWarnings`; it must have no compilation warnings. Wait for the policy binding to take effect.
3. Run `python3 deploy/kubernetes/bootstrap-fence.py --kubeconfig /absolute/private/config --context your-context flumic-workers flumic-actions`. This reads actual UIDs and patches annotations with UID/resourceVersion preconditions. Put those freshly printed UIDs into the target file. Never copy an old namespace UID after recreating a namespace. Restrict namespace modification to trusted operators.
4. Apply `rbac.yaml`. The controller has only namespaced lifecycle rights and GET access to the two named namespaces. Do not run the controller with the bootstrap administrator credential. If changing names, change RoleBindings and ClusterRole resourceNames too.
5. Apply `network-policies.yaml` before enabling action scheduling. The bridge template intentionally permits no egress. Add only your approved destinations (including DNS if required), verify denial and allowed traffic on **every eligible node**, then record the evidence. An existing permissive policy can negate these denies because policies are additive. Workers need separately controlled access to the Control Pane, Hatchet and approved provider/source hosts; their namespace policy is deployment-specific.
6. Configure kubelet `pod-max-pids=128` on every eligible node and qualify the effective cgroup limit from inside a Pod. This is trusted node configuration, not a Pod resource field. Set qualification booleans only after measuring enforcement; evidence is an operator record identifier, not a secret.
7. Create `flumic-hatchet-transport` in the worker namespace through your secret-management process. It needs `HATCHET_CLIENT_TOKEN`; optional keys are `HATCHET_CLIENT_HOST_PORT`, `HATCHET_CLIENT_SERVER_URL`, `HATCHET_CLIENT_TLS_STRATEGY`. Do not put credentials in this repository, target JSON, screenshots or command history. API transport uses verified TLS; worker/Hatchet transport settings must match the deployment.
8. Build and pin approved images using [helper-image.md](helper-image.md). Verify worker shared-v1 protocol, node architecture, image digest, StorageClass and endpoint reachability. Provision pull secrets in both namespaces when needed. The target JSON references secret names, not secret values.
9. Copy `target.example.json` outside the repository to a private mounted file. Replace placeholder UIDs/digests/endpoint and complete qualification fields. Mount it into **both API and reconciler at the same path**, set `CONTROL_RUNTIME_TARGETS_FILE`, and recreate both processes. Production Kubernetes adapters require PostgreSQL and the current migrations. Keep encryption keys stable.
10. Open **Runtime targets**, then **Workers → Add shared worker**. Choose a pool and the target. Creation is stopped; start it explicitly. Inspect desired state, Kubernetes observation and Hatchet registration separately.

On every mutation the controller validates actual Namespace UID, the operator annotation and paired permitted/rejected dry-run ConfigMap probes. This fails closed if admission fencing is missing. The admission rule protects updates that try to remove the fence annotation as well as creates. Namespace administrators remain trusted: copying an obsolete UID annotation into a new namespace defeats operator intent.

## Dedicated k3d test environment

`k3d cluster create --config deploy/kubernetes/k3d.test.yaml` creates **only** `flumic-issue17`; first ensure that name is unused. Export its kubeconfig to a dedicated mode-0600 file and always pass its explicit context. The template disables global kubeconfig updates and configures a 128-process Pod ceiling on both nodes. Create a dedicated registry for this test; never reuse another project's registry or change existing Docker workloads. Import images with `k3d image import IMAGE --cluster flumic-issue17`, or push to that owned registry and pin the resulting digest. Host `localhost` is not the same endpoint inside a Pod. Deploy a separate fixture Control Pane/Hatchet or expose only fixture endpoints through a reviewed host bridge; do not redirect existing workers or upgrade the live database.

## Teardown and retention

Stop workers and wait for Pods to terminate. Removing a worker retains its private PVC and database history; inspect replay requirements before an operator deliberately deletes that exact PVC UID. Jobs are suspended before cascading deletion, with durable cleanup state. Never bulk-delete by a loose label selector to clear a warning. Namespace/UID/spec drift requires investigation and manual reconciliation. Delete the dedicated test cluster only after preserving sanitized qualification evidence and verifying ownership.
