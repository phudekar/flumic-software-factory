# Bootstrap worker profiles

These commented files are shared by standalone workers and control-plane bootstrap:

- [`default.yaml`](default.yaml): `simple` worker type, with API-based planning,
  triage and review defaults.
- [`developer.yaml`](developer.yaml): `developer` worker type, using the Codex CLI.

Every YAML field has a comment explaining its purpose. Missing settings and task
entries inherit the selected factory revision. The loader resolves the result
into a saved profile, assigns its stable identity and revision, and pins the
current factory revision. No credentials or installation-specific database IDs
belong in these files.

The API validates bootstrap files using the same schema, adapter allowlist and
credential checks as profiles saved through the control pane. For the control plane, files are imported
only when the profile store is empty. Standalone workers read them through the
root manifest on every start. The `worker` block holds registration and path policy;
`document` supplies local settings and per-task model/prompt overrides. Compatibility
names `simple-observed` and `developer-observed` are generated by the loader. Existing profiles, their revision history
and running workers are preserved on restart; editing a YAML file does not
publish a new revision into an existing installation.

For an existing installation, create or clone a profile in **Configuration →
Worker profiles** and copy the desired `document.settings` and `document.tasks`
values into the JSON editor. Set the name and base worker type separately. Do
not reset the database to apply a template edit. With PyYAML installed, you can
convert the example document for the editor:

```sh
python3 -c 'import json,yaml; print(json.dumps(yaml.safe_load(open("config/worker-profiles/default.yaml"))["document"], indent=2))'
```

Shared repository, workflow routing, engine retry/timeouts, labels, state and
scan settings remain in the factory configuration. Startup scripts are trusted
operator code and run on each worker start. Access credentials stay in the
injected environment. Saved profile changes apply on the worker's next restart;
use the control pane's Restart action to load an updated worker image too.

## Building managed worker images

The templates now opt into managed image assembly: `default` uses
`python:3.12-slim`, and `developer` uses `node:24-bookworm-slim`. The build installs
the factory runtime and selected coding tool. Set `base_image: ''` to keep using
legacy prebuilt images. `system_packages` and `image_setup_script` add cached
build dependencies; `startup_script` runs each time a container starts.
CLI package versions are pinned in the profile. New image settings are copied
when cloning and versioned with every profile revision. See
[worker image architecture](../../docs/worker-image-builds.md).
